# CLAUDE.md — project briefing for Claude Code

This file is auto-read at the start of every Claude Code session in this directory. It describes the codebase as it currently exists.

## What this project is

**Periodic Table** is a desktop utility, sibling to [Latex-Floater](../Latex-Floater): an interactive periodic table, styled after the widget Google shows for a "periodic table" search — an 18-column grid of all 118 elements, colour-coded by category, with a knowledge panel that shows an element's facts when you click it. Like Latex-Floater it carries a battle pass with unlockable themes, but unlike Latex-Floater it is a normal resizable window, not a tiny always-on-top floater: a full grid plus a detail panel needs real room to be legible, which a floater's shape doesn't comfortably give.

## Stack (decided — matches Latex-Floater, don't re-evaluate without a reason)

- **Tauri 2** for the shell (Rust, in `src-tauri/`), same reasoning as Latex-Floater: a tiny installer and low idle RAM by rendering in the OS's own web view instead of shipping a bundled browser.
- **No framework, no bundler** in the renderer — plain HTML/CSS/JS, same as Latex-Floater. Tauri serves `src/` as-is.
- **No third-party JS at all**, unlike Latex-Floater (which vendors MathQuill/jQuery/MathJax). This app doesn't need a math editor or an export pipeline — the only external input is `src/data/elements.json`, which is generated once by `scripts/build-data.js` and committed, not fetched or vendored at build time.
- **IBM Plex** (Sans + Mono), self-hosted in `src/fonts/`, copied verbatim from Latex-Floater. Same accent amber `#d4a45c`.
- **Rust dependencies are minimal, and smaller than Latex-Floater's**: `tauri` (no `image-png` feature — nothing here is rasterised) and `tauri-plugin-window-state`. No clipboard plugin (nothing is copied out of this app), no global-shortcut plugin (this isn't meant to be instantly summoned), just per-platform `windows-sys` / `objc2-app-kit` for window opacity, same as Latex-Floater.

## Where the data comes from

`src/data/elements.json` is generated by `scripts/build-data.js` from [Bowserinator/Periodic-Table-JSON](https://github.com/Bowserinator/Periodic-Table-JSON), a public 118-element dataset. The script keeps only structured factual fields — `number, symbol, name, category, group, period, block, phase, atomic_mass, density, melt, boil, electron_configuration, electronegativity_pauling, discovered_by, named_by, xpos, ypos` — and writes an additional `summary` field: a short, original one-sentence description generated from those facts (e.g. *"Iron (Fe) is the 26th element, a transition metal with an atomic mass of 55.845 u. Solid at room temperature. Discovered by ~5000 BC."*). The upstream dataset's own prose `summary` field and its photo URLs are deliberately **not** used — both read as adapted from Wikipedia/Wikimedia with unclear per-element licensing, whereas facts (atomic mass, category, etc.) aren't copyrightable, and an originally-generated sentence sidesteps the question entirely.

**`xpos`/`ypos` already encode the standard pulled-out layout** — verified by inspecting the actual data (`node -e "require('./src/data/elements.json')..."`): lanthanides sit at `ypos: 9` and actinides at `ypos: 10`, both spanning `xpos: 3` through `17`, with `ypos: 1`–`7` holding the normal 18-column block. Row 8 is intentionally empty — the visual gap above the f-block. No separate "widescreen" field (`wxpos`/`wypos`, which the upstream dataset also has) is needed or stored.

The script is a one-off: run `npm run build-data` manually if the upstream dataset changes; it is not part of `npm run dev` or `npm run build`.

## Key architectural decisions and why

**The renderer is shell-agnostic; `bridge.js` is the seam** — identical philosophy to Latex-Floater. `periodic-table.js`, `knowledge-panel.js`, `battlepass.js` and `app.js` are written entirely against `window.floater`, built here on top of `window.__TAURI__`. Its surface is smaller than Latex-Floater's: `togglePin`, `getPinState`, `minimize`, `close`, `setOpacity`, `resizeBy`, `getBounds`, `restoreBounds`, `setMinHeight`, `platform` — no `copyText`/`copyImage`/`renderPng`, since nothing in this app is exported.

**Only one thing crosses into Rust**: `set_opacity`, ported verbatim from Latex-Floater (`WS_EX_LAYERED` + `SetLayeredWindowAttributes` on Windows via `run_on_main_thread`, `NSWindow.setAlphaValue` on macOS — same caveat as Latex-Floater: the macOS branch has not been compiled or run on an actual Mac). Window chrome — pin, minimize, close, drag — uses Tauri's JS window API directly, gated by `capabilities/default.json`.

**Every JS module that isn't `bridge.js` or `app.js` is wrapped in an IIFE.** `battlepass.js` always was; `periodic-table.js` and `knowledge-panel.js` were not in an early draft, and since none of these files are ES modules (`index.html` loads them as plain `<script>` tags, and top-level `const`/`let` in separate non-module `<script>` tags share the same global lexical scope in a browser), both files independently declaring `const CATEGORY_CLASS = {...}` at top level threw `Uncaught SyntaxError: Identifier 'CATEGORY_CLASS' has already been declared` and broke the whole page — caught by loading the app in a browser tab (see "Testing without a compiled build" below) before it ever reached a real Tauri build. Fixed by wrapping both in `(function () { 'use strict'; ... })();`, matching `battlepass.js`'s existing convention. Any new top-level renderer file should follow the same pattern unless it's meant to export something onto `window`.

**The knowledge panel is a permanent side panel, not an overlay.** Latex-Floater's history box slides in over the editor because the floater is small and history is occasional; here the window is wide enough for the grid and the panel at once, and clicking through many elements in a row is the expected way to use the app, so a toggle would only get in the way. `knowledge-panel.js` loads before `periodic-table.js` in `index.html` specifically so `PeriodicTable.select()` can call `window.KnowledgePanel.show(el)` unconditionally.

**Category colours are a fixed palette, not theme-derived.** `styles.css` defines ten `--cat-*` custom properties (alkali metals through unknown) that don't change between dark and light mode and aren't touched by any battle-pass theme — they're the periodic table's own factual colour coding, the same way Latex-Floater's math glyphs follow `--fg` rather than `--accent`. Cell and knowledge-panel-header text uses a single fixed dark colour (`--cat-text`) rather than following the theme, since these swatches are mid-saturation pastels that need consistent dark text regardless of what mode or theme is active.

**The battle pass is the same engine, retargeted.** `battlepass.js` is carried over from Latex-Floater with one substantive change: XP is awarded once per element the first time its knowledge panel is shown (a permanent `viewed` set of atomic numbers, persisted in `localStorage` as `bpViewed`), not on every "commit" the way Latex-Floater awards per copied/cleared expression. `XP_PER_ELEMENT = 150` is flat (no length/structure bonus — there's no equivalent complexity signal for viewing an element) and tuned so all 118 elements (17,700 XP) comfortably clears the fifty-level curve's ~16,170 XP total. The level curve, theme-unlock schedule, track UI, paint-brush dropdown and dev shortcuts (`Ctrl+Shift+Alt+L`/`R`) are unchanged; resetting via the dev shortcut also clears `viewed`, so previously-seen elements pay out again.

**Battle-pass window growth reuses Latex-Floater's snapshot/restore pattern.** Opening the track grows the window by `PASS_HEIGHT` (plus any shortfall if `.table-view` is already below its own `--table-min-height`), and closing it restores the window's exact pre-grow `{y, height}` via `getBounds()`/`restoreBounds()` in `bridge.js` — not a `resizeBy(-need)` reversal, for the same non-100%-DPI rounding-drift reason documented in Latex-Floater's `bridge.js`. Unlike Latex-Floater there is no graph panel competing for the same logic, so `updateMinHeight()` in `app.js` is simpler: the minimum is just `500 + (pass open ? trackHeight : 0)`.

## Conventions

Same as Latex-Floater:

- **Comments explain the *why*, not the *what***. Prefer a paragraph at the top of a logical section over sprinkled inline comments.
- **No bullet-point overuse in user-facing copy** (README, error/status text). Write in sentences.
- **CSS variables over hardcoded colours**, except the fixed `--cat-*` category swatches (see above), which are deliberately theme-independent.
- **Native surface stays minimal.** If something can be done in the renderer, do it there.
- **Files use CRLF line endings** (the repo was created on Windows, same as Latex-Floater). Keep new files consistent.

## Testing without a compiled build

The frontend has no shell dependency beyond `window.__TAURI__`, so it can be exercised in an ordinary browser tab by serving `src/` with any static file server and injecting a small stub that defines `window.__TAURI__` (a `getCurrentWindow()` returning stub `setSize`/`outerPosition`/etc., plus `LogicalSize`/`LogicalPosition`) before `bridge.js` loads. This is how the grid layout, knowledge panel data, theme switching, XP award/dedup and the battle pass track were all verified during initial development, without waiting on a Rust compile each time. It won't catch anything native (`set_opacity`, the boot-time window-size clamp) — those still need a real `npm run dev`.

## Things that are intentionally NOT in v1

- **No parameter sliders, no search/filter box.** The plan explicitly scoped this to the grid + knowledge panel + battle pass; nothing beyond that was requested.
- **No cloud sync of settings or battle-pass progress.** Everything is local (`localStorage` plus the window-state plugin's file), same as Latex-Floater. XP and unlocked themes don't follow you between machines.
- **No macOS build yet.** Same caveat as Latex-Floater: `set_opacity`'s macOS branch (`objc2-app-kit`) has not been compiled or run on an actual Mac.
- **No code signing.** Windows SmartScreen will warn on first run; macOS Gatekeeper will require right-click → Open. Fine for personal use, not for wider distribution.

## Running locally

```powershell
npm install
npm run dev      # tauri dev: hot-reloads src/, rebuilds Rust on change
npm run build    # installers in src-tauri/target/release/bundle/
```

Requires Node 18+, Rust (rustup), and on Windows the MSVC build tools (any Visual Studio with "Desktop development with C++"); on macOS, Xcode command line tools. The first build compiles several hundred crates and takes a few minutes; later builds take seconds.

## If something breaks

- **Blank window or a `CATEGORY_CLASS`/similar "already declared" error in devtools**: a new top-level renderer file isn't wrapped in an IIFE and collides with another script's top-level declaration — see the architectural note above. Wrap it.
- **`window.__TAURI__` is undefined**: `app.withGlobalTauri` was turned off in `tauri.conf.json`, or the page is being opened directly in a browser without the stub described above.
- **Grid is empty but no console error**: `periodic-table.js` fetches `data/elements.json` relative to `src/`; confirm that file exists and is valid JSON (`npm run build-data` regenerates it).
- **A titlebar button or drag does nothing, with a permission error in devtools**: the corresponding `core:window:allow-*` permission is missing from `capabilities/default.json`.
- **Window appearing off-screen or at a stale size**: delete the window-state plugin's file — `%APPDATA%\com.local.periodictable\.window-state.json` on Windows, `~/Library/Application Support/com.local.periodictable/.window-state.json` on macOS.
- **Opacity slider does nothing**: `set_opacity` in `lib.rs` is platform-specific; on an unsupported platform it's a no-op by design.
- **Rust build fails on Windows with a linker error**: MSVC build tools aren't installed or not the x64 variant. On macOS, `xcode-select --install`.
